# 面向中小型网络的自动化巡检与故障诊断平台分批开发归档

## 1. 拆分目标

本归档用于把《面向中小型网络的自动化巡检与故障诊断平台_毕设实施计划.md》中的总体方案拆成可分批开发、可阶段验收、可支撑论文和答辩的实施路线。

项目核心目标不是一次性堆满所有功能，而是先形成“资产录入 -> 巡检执行 -> 结果留痕 -> 故障诊断 -> 可视化展示 -> 报告导出”的完整闭环，再逐步补强告警、趋势、拓扑、资产发现等高分功能。

考虑到 Windows 本机、Linux 虚拟机、答辩现场网络和 Python 依赖版本可能带来的环境差异，项目开发和演示环境采用 Docker Compose 作为主方案。整体形态采用“微服务式容器部署”，即把后端、前端、数据库、演示目标服务、反向代理等运行环境拆成独立容器，但业务代码不做过度分布式拆分，避免本科毕设范围失控。

## 2. 三种拆分方式对比

### 2.1 按技术层拆分

做法：先搭后端，再搭前端，最后联调。

优点：

- 技术边界清楚。
- 后端接口可以较早稳定。
- 适合团队中前后端人员分工明确的情况。

缺点：

- 前期看不到完整演示效果。
- 容易出现后端做完但前端联调时间不足的问题。
- 对毕业设计答辩不够友好，因为阶段性成果不直观。

结论：不作为主路线，只作为每一批内部的工作顺序。

### 2.2 按功能模块拆分

做法：资产管理、巡检任务、检测器、诊断、告警、报表、看板分别独立开发。

优点：

- 和论文功能模块对应关系清楚。
- 每个模块职责明确，便于写系统设计章节。

缺点：

- 单个模块完成后未必能形成可演示闭环。
- 模块之间依赖较多，容易在后期集中暴露联调问题。

结论：适合作为论文组织方式，不适合作为主要开发顺序。

### 2.3 按可演示闭环拆分

做法：每一批都尽量形成可运行、可截图、可测试的小闭环，先做最小可交付版本，再增加高分能力。

优点：

- 每批都有可验收成果。
- 适合毕业设计持续截图、写测试记录、准备答辩材料。
- 即使后期时间不足，也能保住最小可答辩版本。
- 能把风险较高的功能放到后置扩展批次。

缺点：

- 需要每批都做少量前后端联调。
- 初期需要先定义好核心数据模型，避免后续频繁改表。

结论：推荐采用。后续批次均按“可演示闭环优先”推进。

## 3. 推荐总体路线

推荐路线分为 8 个批次：

| 批次    | 名称         | 核心目标                      | 答辩价值            |
| ----- | ---------- | ------------------------- | --------------- |
| 第 0 批 | Docker 项目初始化与基础架构 | 搭建项目骨架、容器编排、数据库、接口规范和演示环境 | 为后续开发和答辩演示打基础 |
| 第 1 批 | 资产台账闭环     | 完成登录、资产增删改查和资产状态字段        | 证明系统不是单一脚本，而是平台 |
| 第 2 批 | 巡检执行闭环     | 完成 Ping、端口、HTTP 检测和手动巡检任务 | 形成核心技术能力        |
| 第 3 批 | 诊断与结果闭环    | 保存巡检结果并生成故障诊断建议           | 体现故障诊断主题        |
| 第 4 批 | 看板与报告闭环    | 仪表盘展示、结果查询、Excel 报告导出     | 形成完整可演示 MVP     |
| 第 5 批 | 告警与阈值策略    | 告警生成、确认、恢复、连续失败判定         | 提升工程完整度         |
| 第 6 批 | 高分扩展能力     | DNS、资产发现、趋势、逻辑拓扑、日志审计     | 提升论文和答辩亮点       |
| 第 7 批 | 测试、部署与论文材料 | 场景测试、截图、演示脚本、论文支撑材料       | 准备最终答辩          |

主线必须优先保证第 0 批到第 4 批完成。第 5 批和第 6 批属于推荐高分版本，第 7 批贯穿后期收尾。

## 3.1 Docker 微服务式部署设计

### 3.1.1 服务拆分

采用 Docker Compose 管理以下容器：

| 服务名 | 作用 | 必要性 |
|---|---|---|
| `netcheck-backend` | FastAPI 后端，提供 REST API、巡检任务、诊断规则、报告生成 | 必做 |
| `netcheck-frontend` | Vue 3 前端，提供登录、资产、巡检、看板、报告页面 | 必做 |
| `netcheck-db` | 数据库服务，开发期可用 SQLite volume，推荐演示期使用 MySQL | 推荐 |
| `netcheck-nginx` | 统一入口和静态资源代理，也可作为正常 HTTP 演示目标 | 推荐 |
| `demo-web-ok` | 正常 Web 服务，用于 HTTP 正常场景 | 必做 |
| `demo-web-error` | 返回 500 的 Web 服务，用于 HTTP 异常场景 | 必做 |
| `demo-web-slow` | 延迟响应服务，用于响应时间超阈值场景 | 必做 |
| `demo-port-open` | 开放固定 TCP 端口的服务，用于端口正常场景 | 推荐 |
| `demo-dns` | 可选 DNS 演示服务，用于后续 DNS 检测 | 可选 |

这种拆分体现“微服务式部署”，但业务核心仍保留在后端服务内。后端内部通过模块化目录拆分资产、任务、检测器、诊断、告警和报告，不把每个业务模块拆成独立微服务。这样既能体现容器化工程能力，又能控制毕设开发复杂度。

### 3.1.2 网络设计

Docker Compose 内部创建专用网络，例如 `netcheck-lab`。平台巡检时优先检测 Compose 网络内的演示服务，例如：

- `demo-web-ok:80`
- `demo-web-error:80`
- `demo-web-slow:80`
- `demo-port-open:22` 或自定义端口

演示资产可以使用容器服务名或固定容器 IP。论文和答辩中说明：Docker 环境用于构造稳定可复现的巡检实验网络；真实局域网巡检作为扩展能力，可在 Linux 虚拟机或宿主机网络中验证。

### 3.1.3 数据持久化

数据库和报告文件必须挂载 volume：

- `db_data`：保存数据库数据。
- `report_data`：保存 Excel 报告。
- `backend_logs`：保存后端日志。

这样容器重启后数据不丢失，也方便答辩前准备固定数据。

### 3.1.4 端口规划

建议端口：

| 服务 | 容器端口 | 宿主机端口 |
|---|---:|---:|
| 前端入口 | 80 | 8080 |
| 后端 API | 8000 | 8000 |
| MySQL | 3306 | 3306 或不暴露 |
| 正常 Web 演示服务 | 80 | 18080 |
| 异常 Web 演示服务 | 80 | 18081 |
| 慢响应 Web 演示服务 | 80 | 18082 |

如果使用 `netcheck-nginx` 作为统一入口，可以只暴露 `8080`，由 Nginx 转发 `/api` 到后端，前端页面和接口都通过同一个入口访问。

### 3.1.5 技术边界

Docker 是本项目的开发、部署和演示基础，不等同于把系统改成复杂微服务架构。主线不引入 Kubernetes、服务注册中心、消息队列集群、分布式链路追踪等内容。这些可以写入论文展望，不进入必做范围。

## 4. 分批开发计划

### 第 0 批：Docker 项目初始化与基础架构

目标：搭建可运行的 Docker Compose 开发和演示环境，确定前后端项目骨架、数据库、接口风格和演示服务入口。

范围：

- 创建 FastAPI 后端项目结构。
- 创建 Vue 3 或 Bootstrap 前端项目结构。
- 创建 `docker-compose.yml`。
- 创建后端 `Dockerfile`。
- 创建前端 `Dockerfile`。
- 创建演示服务目录 `demo-services/`。
- 配置 SQLite volume 或 MySQL 容器。
- 接入 SQLAlchemy。
- 设计基础模型和迁移方式。
- 配置统一响应格式。
- 配置日志、异常处理和跨域。
- 准备 5 类演示资产数据。
- 准备正常 Web、异常 Web、慢响应 Web、开放端口等演示目标容器。

建议容器目录：

- `docker-compose.yml`：统一编排后端、前端、数据库和演示服务。
- `backend/Dockerfile`：构建 FastAPI 后端镜像。
- `frontend/Dockerfile`：构建前端镜像。
- `demo-services/web-ok/`：正常 HTTP 演示服务。
- `demo-services/web-error/`：HTTP 500 异常演示服务。
- `demo-services/web-slow/`：慢响应演示服务。
- `volumes/reports/`：报告导出挂载目录。
- `volumes/logs/`：日志挂载目录。

建议后端目录：

- `backend/app/main.py`：FastAPI 入口。
- `backend/app/core/config.py`：系统配置。
- `backend/app/core/database.py`：数据库连接。
- `backend/app/models/`：数据库模型。
- `backend/app/schemas/`：请求和响应结构。
- `backend/app/api/`：接口路由。
- `backend/app/services/`：业务服务。
- `backend/app/checkers/`：巡检检测器。

建议前端目录：

- `frontend/src/api/`：接口请求封装。
- `frontend/src/views/`：页面。
- `frontend/src/components/`：通用组件。
- `frontend/src/router/`：路由。

完成标准：

- `docker compose up -d` 能启动全部基础容器。
- 后端能在容器中启动并访问健康检查接口。
- 数据库能通过 volume 持久化数据。
- 前端能在容器中启动并访问基础页面。
- 后端容器能访问 `demo-web-ok`、`demo-web-error`、`demo-web-slow` 等演示服务。
- 至少有一份初始化演示数据脚本。

归档材料：

- 项目启动说明。
- Docker Compose 服务说明。
- 技术栈说明。
- 初始数据库表说明。
- 系统架构草图。

### 第 1 批：资产台账闭环

目标：完成“登录 -> 资产管理 -> 资产状态维护”的基础平台能力。

范围：

- 管理员登录和退出。
- 简化 token 或 session 登录状态保持。
- 资产新增、编辑、删除、查询。
- 按资产类型、区域、状态筛选。
- 资产字段包含名称、IP、主机名、类型、区域、端口、负责人、备注、当前状态。
- 前端实现登录页和资产管理页。

必须完成：

- 管理员登录。
- 资产列表。
- 新增资产。
- 编辑资产。
- 删除资产。
- 条件查询。

暂缓内容：

- 复杂角色权限。
- 多用户细粒度权限。
- 批量导入导出。

完成标准：

- 登录后可以进入系统。
- 可以维护至少 10 条资产数据。
- 资产数据能持久化保存。
- 资产管理页面能支撑论文截图。

归档材料：

- 资产表字段说明。
- 资产管理接口清单。
- 登录与资产管理页面截图。

### 第 2 批：巡检执行闭环

目标：完成“创建巡检任务 -> 执行检测 -> 得到原始结果”的核心巡检能力。

范围：

- 巡检任务创建、编辑、启用、停用。
- 手动立即执行任务。
- 巡检对象选择。
- Ping 检测。
- TCP 端口检测。
- HTTP 状态码和响应时间检测。
- 检测器统一封装为 `BaseChecker`、`PingChecker`、`PortChecker`、`HttpChecker`。
- 任务状态包括待执行、执行中、已完成、执行失败。
- 保存任务执行日志。
- 巡检目标优先使用 Docker Compose 内部服务名，保证演示环境稳定。

必须完成：

- 手动巡检任务。
- Ping 检测。
- TCP 端口检测。
- HTTP 检测。
- 巡检结果落库。

暂缓内容：

- APScheduler 定时任务。
- DNS 检测。
- TLS 证书检测。
- 任务取消和重试。

完成标准：

- 可以选择资产并执行巡检。
- 巡检后能看到每个资产的检测结果。
- 结果中包含检测类型、检测状态、响应时间、错误信息和检测时间。
- 离线主机、端口关闭、HTTP 异常、响应慢四类场景能通过 Docker 演示服务稳定复现。

归档材料：

- 检测器类图或说明。
- 巡检任务流程图。
- 巡检结果样例。
- 异常场景测试截图。

### 第 3 批：诊断与结果闭环

目标：把原始检测结果转换为故障诊断记录，体现“故障诊断平台”的主题。

范围：

- 巡检结果列表和详情。
- 根据检测结果生成诊断记录。
- 内置规则化诊断逻辑。
- 输出故障类型、故障等级和处理建议。
- 根据最新巡检结果更新资产当前状态。

基础诊断规则：

| 现象 | 故障类型 | 等级 | 建议 |
|---|---|---|---|
| Ping 失败 | 主机离线或链路异常 | 严重 | 检查主机电源、网线、交换机端口和网关配置 |
| Ping 正常但端口失败 | 服务未启动或防火墙拦截 | 重要 | 检查服务进程、防火墙策略和监听端口 |
| HTTP 4xx | 请求路径或访问权限异常 | 一般 | 检查 URL、权限配置和路由规则 |
| HTTP 5xx | Web 应用内部错误 | 重要 | 检查应用日志、数据库连接和服务负载 |
| 响应时间超过阈值 | 网络拥塞或服务性能下降 | 警告 | 检查链路质量、服务器资源和业务负载 |

必须完成：

- 巡检结果列表。
- 诊断记录生成。
- 故障等级和处理建议。
- 资产状态自动更新。

暂缓内容：

- 可视化规则编辑器。
- 复杂规则引擎。
- 多轮连续失败判定。

完成标准：

- 执行巡检后能自动生成诊断记录。
- 每条异常能看到明确故障类型和建议。
- 资产列表中的状态能随巡检结果变化。

归档材料：

- 诊断规则表。
- 结果到诊断的数据流说明。
- 故障诊断页面截图。

### 第 4 批：看板与报告闭环

目标：完成最小可交付版本，形成可答辩演示闭环。

范围：

- 首页仪表盘。
- 总资产数、在线资产数、异常资产数、今日巡检次数。
- 在线率趋势图。
- 故障类型分布图。
- 最近告警或最近异常列表。
- 巡检结果筛选。
- Excel 报告生成和下载。

必须完成：

- 仪表盘核心指标。
- ECharts 图表。
- 巡检结果查询。
- Excel 报告导出。

暂缓内容：

- PDF 报告。
- 复杂报表模板。
- 多维度历史分析。

完成标准：

- 从登录到生成报告能完整演示。
- Excel 报告包含巡检概况、异常资产、故障类型和处理建议。
- 页面截图足够支撑论文“系统实现”章节。

归档材料：

- MVP 功能清单。
- 报告样例。
- 首页仪表盘截图。
- 完整演示流程截图。

第 0 批到第 4 批完成后，项目达到最小可答辩版本。

### 第 5 批：告警与阈值策略

目标：把异常提示升级为告警闭环，提升运维平台完整度。

范围：

- 告警生成。
- 告警等级。
- 告警确认。
- 告警恢复。
- 告警历史。
- 响应时间阈值。
- 连续失败次数阈值。
- 连续恢复次数阈值。

建议策略：

- 连续 3 次失败后触发告警。
- 告警未恢复前不重复生成同类新告警。
- 连续 2 次正常后标记恢复。
- 支持管理员手动确认。

必须完成：

- 告警列表。
- 告警确认。
- 告警恢复。
- 阈值配置。

暂缓内容：

- 短信、邮件、企业微信等外部通知。
- 告警升级策略。

完成标准：

- 异常资产能生成告警。
- 告警状态能从未确认变为已确认。
- 资产恢复后告警能标记恢复。
- 论文中能说明告警降噪和闭环处理机制。

归档材料：

- 告警状态流转图。
- 阈值策略说明。
- 告警中心截图。

### 第 6 批：高分扩展能力

目标：在不破坏主线的基础上增加亮点功能，提升论文和答辩表现。

优先级从高到低：

1. DNS 检测。
2. 资产发现。
3. 历史趋势分析。
4. 逻辑拓扑图。
5. 操作日志与审计。
6. 批量导入导出。
7. TLS 证书检测。
8. Docker 容器服务检测。

建议只选择 3 到 5 项完成，避免范围失控。

推荐组合：

- DNS 检测。
- 资产发现。
- 历史趋势分析。
- 逻辑拓扑图。
- 操作日志。

完成标准：

- 至少完成 DNS 检测和历史趋势分析。
- 如果时间允许，完成逻辑拓扑图，用颜色区分正常、异常、未知资产。
- 资产发现限制在小网段，例如 `/24`，并加入扫描速率控制说明。

归档材料：

- 高分功能说明。

## 11. 风险控制

### 11.1 范围风险

风险：功能模块过多，后期无法全部完成。

控制方式：

- 第 0 批到第 4 批作为必做主线。
- 第 5 批和第 6 批按时间选择。
- SNMP、Prometheus、K8s 只写展望，不进入主线。

### 11.2 技术风险

风险：Ping 在不同系统下行为不一致，Docker Desktop 在 Windows 上运行于虚拟化网络中，容器扫描真实局域网时可能和宿主机表现不同；扫描大量 IP 也可能耗时较长。

控制方式：

- 优先封装统一检测器接口。
- 演示资产数量控制在 10 到 50 个。
- 网段扫描只支持小网段。
- 默认用 Docker Compose 内部演示服务做答辩演示。
- Ping 检测容器内目标时为后端容器配置必要网络能力，例如 Linux 环境下可考虑 `NET_RAW`。
- 真实局域网扫描在 Linux 虚拟机或宿主机环境中单独验证，不作为 Docker 演示的唯一依赖。

### 11.3 联调风险

风险：后端接口和前端页面后期集中联调导致延期。

控制方式：

- 每批都至少完成一个前后端闭环。
- 接口返回格式从第 0 批固定。
- 每批保留页面截图和测试记录。

### 11.4 答辩风险

风险：现场网络环境不稳定导致演示失败。

控制方式：

- 准备 Docker Compose 本地模拟资产。
- 准备固定测试数据。
- 准备系统截图。
- 准备演示视频作为备份。

## 12. 当前归档结论

项目采用“Docker Compose + 可演示闭环分批”的开发方式。

主线目标是先完成第 0 批到第 4 批，形成基于 Docker 的最小可答辩版本；随后根据时间完成第 5 批和第 6 批中的高分能力；最后通过第 7 批把系统成果转化为论文、测试和答辩材料。

下一步应进入第 0 批：Docker 项目初始化与基础架构。
